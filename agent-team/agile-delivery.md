# 敏捷研发的任务与分工

项目经理先读原任务、所属目标、依赖和最新反馈，确认交付的是一个可体验的软件增量。以用户能观察的结果识别研发故事。已有开工判断、标准或实测材料可直接复核并引用。前提具备时在原故事开始「敏捷研发」，调研和目标计分分别使用对应的方法。项目经理记录待满足的条件、责任人和恢复事件，处理交接中断。

| 工作步骤 | 执行人 | 验收人 | 交付和退回依据 |
| --- | --- | --- | --- |
| 定义增量与验收标准 | 需求分析师 | 用户故事评判员 | 用同一业务术语给出触发条件、结果和反例，每条标准有编号与版本。词义或范围有变，回到原标准修订。 |
| 设计测试用例 | 验收自动化工程师 | 研发经理 | 在标准下登记可复现的用例、独立预期和能识别的错误实现。涉及旧行为时固定独立基线。用例不足退回设计者。 |
| 实现并验证候选提交 | 研发实施小队 | 代码审查员 | 研发经理作为队长按技术栈选一名实现负责人；成员取得真实的协作运行，交回代码、分支、完整提交及红绿或回归证据。队长核对同一候选并提交本步。代码审查员独立抽查断言与实现，缺陷附复现条件。 |
| 演示与独立终验 | 运行验证员 | 质量交付经理 | 在交付环境从实际用户入口复演正反例，注明覆盖范围和证据。终验人按当前标准版本和候选逐项批准，或指明标准、用例和退回步骤。 |

第三步的工作方法负责人配置为**小队**。系统先唤醒队长；具体工程师由队长在本故事派出，并读回接手人和运行 ID。Go 服务、React 页面、Electron 客户端和 CLI 分别匹配已有技术专家；跨栈增量由同一位工程师负责集成。队员提供证据，队长负责方法送审。已经提交的步骤被退回时，平台优先找上次实际提交人，队长按原记录把补正派到对应实现者。流程历史应能分别回答“谁写代码”“谁提交候选”“谁独立审过”。

每次交接记录标准版本、用例编号、仓库、分支、完整 SHA、可复现入口和证据，字段随步骤逐步补齐。需求调整回到标准；断言不能识别错误回到用例；候选变化或用例失败回到实现；演示环境缺失回到演示。技术环境故障单列未验证。使用当前方法修订提交、批准或退回，平台同步看板并派工。普通看板审核、受保护分支签核、发布及日常升级继续按各自入口执行。

验收这套分工时，选一个确实需要更改代码的故事。除了核对四步十项、退回与终验，还要从第三步找回实际工程师运行、失败断言或原行为基线、提交后的通过记录，再核对审查人与实现人。仅复验已发布候选能验证回归路径；新功能的测试先行和小队内派工需要单独实跑。

需求分析师和故事评判员从领域词义中选一组可区分结果的场景，验收自动化工程师把同一组场景写成独立断言。实现人与终验人按各自步骤使用已绑定的 [xshadow-story-evidence](skills/xshadow-story-evidence/SKILL.md)，在原用例下记录基线、候选和实际差异。涉及建模或测试策略选择时，按技能中的经验编号查适用条件。

## 个人第二大脑的协作

在目标计划中为同类功能故事选择「敏捷研发 · 个人第二大脑」。[工作方法模板](work-methods/second-brain-agile.json)保存完整的四步十项及角色绑定。迁移时按目标工作区的 `team.json` 角色和小队键替换 `{{agent:…}}`、`{{squad:…}}` 为实配 ID。更新已有方法使用原方法 ID 与当前 `base_revision`，读回目录修订。已开工故事按实例快照推进。支持 `adopt_revision` 的服务允许成员在执行中显式采用兼容的目录修订，当前步骤及后续工作使用新版，原签核保留当时的条文。

先由验证角色从获准原件确定预期，再由一名工程师在主仓实现，代码审查员按同一候选独立复核。角色顺序交接，已裁定事项引用原回执。

集成人将候选完整提交及用例证据直接挂回原事项，队长和代码审查员读取同一份记录。队长持有方法送审权，按候选提交一次。代码审查员检查实现与断言，运行验证员核对现场，质量交付经理按原标准终验。正式评审通过原方法派工。补正按同一标准修订、用例、候选和入口查找首个差异，只给对应责任人新的观察与证据位置。项目经理在依赖、派工或跨角色协作需要协调时介入。

### 领域规则的审核位置

在「设置 → 工作流 → 工作方法」展开方法和相应步骤，「执行说明」给出职责，「验收项」列出独立审核所用的判据。工作区成员可从方法下方的「编辑方法」更新目录修订。通用「敏捷研发」与项目专用方法各有独立定义。已执行的步骤仍按当时的实例修订回查签核。

DDD 从影响当前交付的一条规则开始。以证据身份为例，需求分析师与用户故事评判员核对“索引中的命中”和“获准原件的出现位置”各由谁确认。验收自动化工程师与研发经理用两个正反例排除按搜索行计数、按文字合并两种错误实现。集成人和代码审查员核对该不变量在同一候选的实现和回归证据。运行验证员从用户入口复演，质量交付经理由实测回查原规则与修订。词义不清回到标准，断言无辨别力回到用例，代码失守回到实施，入口缺证回到演示。平台核对结构化账本、版本及勾选结果，领域词义和正反例由独立验收人结合原件判定。
