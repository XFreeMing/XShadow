任务统一按用户故事规划和交付。每个新建或重新规划的交付任务写清：谁在什么场景下，希望获得什么结果、解决什么问题；本次交付的具体产物；用户取得或体验产物的入口；可观察的验收条件；一名交付负责人及范围边界。标题直接写用户得到的结果。报告、分析结论、可运行工具和可体验功能都可以是产物，但必须能被用户取得和使用。

新建或正式重规划的故事先取得独立的可开工结论，退回时按具体反例和责任人修正。验收测试从已认可的标准映射到用例、命令、预期、版本和证据；质量交付经理在同一候选版本上逐条记录通过、失败或未验证，必验项缺证据或失败不得整体通过。

## 任务上下文与验收依据

接任务时、每次新的实质讨论或交接时、以及终验前，都重新读取当前任务的上下文。接收方自己读取；上一条消息中的转述、引用和旧结论不算新事实，与当前记录冲突时以当前记录为准。上下文分三层，引用时写清来源：

- 上层目标：任务正式归属的目标，及其最新的意图、范围和整体验收条件。
- 故事：任务自身的标识、版本、完整正文、结果与贡献，以及近期生效的反馈。
- 有效目标：有正式上层目标时就是该目标；没有时有效目标就是当前故事本身，明确写出而不是只报“无”。

贡献优先采用故事中明确写出的贡献；没有时可采用正式计划里绑定本任务的节点 outcome，或故事正文首段用户故事，并注明来源。不得把标题、同项目其他目标或其他任务的内容当成贡献或验收条件。上层目标的验收条件与故事的验收条件分别标明归属；正文没有可提取的验收条件时如实标注“信息不足”并引用来源，不以标题补全。最终结果或成功标准发生实质变化时，重审整份计划及所有关联故事；路线或做法改变时，只重评受影响的依赖和相关故事。普通交接或目标措辞更新不自动授权开始新工作，也不改变既有授权。

读取入口：先确认注入 CLI 是否支持该能力——运行 `"$MULTICA_CLI_PATH" issue --help`，在命令列表中找到 `context` 才可直接调用 `"$MULTICA_CLI_PATH" issue context <任务标识> [--output json|text]`；退出码为 0 不代表支持，因为旧版会把未知子命令显示为 issue 帮助。旧版发行没有 `context` 时，使用本机已 provision 的专用只读入口：Linux/macOS 为 `"$HOME/.local/bin/multica-goal-context"`，Windows 使用用户已配置的绝对路径；调用形式同为 `issue context <任务标识> [--output json|text]`。该入口固定当前任务身份和服务器、工作区，只允许 `issue context` 的单个任务和 `--output`，其他指令应被拒绝；不要从业务仓库或 PATH 中随意执行同名文件。两条入口都只读，不切换 profile，不查找、复制或输出凭据；其余 multica 命令继续使用注入的 `$MULTICA_CLI_PATH`。读取失败或返回结构异常按错误处理，不当作“没有目标”。
