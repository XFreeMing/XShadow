# 按用户故事交付任务

每张新建或重规划的卡都从用户结果写起。负责人和状态用原事项字段，领域规则、用例和实测回执用原验收台账。卡片正文只需以下内容。

## 任务正文

1. **归属与结果**　链接目标，用一句话说清这张卡完成后谁能做成什么。
2. **目标成果图**　把入口、操作和结果按体验顺序画成一组图并内嵌在正文。更新、冲突、拒绝和越权等影响验收的不同状态独立成图。标明规划示意，使用具体样例。
3. **怎么验**　写一个能实际操作的检查，链接完整范围、用例和证据。交付后附真实体验入口。

## 开工评判与验收映射

新建或正式重规划的故事先由用户故事评判员给出可开工或退回结论，再进入实现。开工只要求写明预定的交付入口、验收方法和必要输入，不要求产物已经存在；实际入口、产物和用户可达性在终验时核对。退回必须给出具体反例和责任人，由原负责人修正；评判员不自行改写故事。可开工后先固定预期，再实现并按同一版本独立验收。

验收自动化工程师把已认可的验收条件逐条映射为可运行的用例、命令、预期结果、执行版本和证据位置；优先复用已有测试并说明依据。无法自动化的手验项说明原因、步骤和负责人。跨入口影响、旧测试复用、范围或版本变化时按影响重验，未重验项写明理由。

质量交付经理对同一候选版本逐条记录通过、失败或未验证；必验项缺证据或失败时不得整体通过，并注明责任人、回流路径和用户体验决定。候选版本可验收时事项进入审核中，由验收自动化工程师按冻结标准实跑并推进：全部必验标准通过才 done，失败或未验证回到原交付团队修复。同一标准版本至少三轮不同且真实失败的独立验收，并且团队负责人明确已无可执行方案，才产生一项指派给用户的决策事项；重放、评论或运行次数、缺证据、未验证和环境错误不计真实失败。

简单或报告类故事轻量处理：写明使用者、产物、入口和可核对条件即可，不为填表另建文档、审批层、每阶段事项或重复唤醒。

拆分故事时，每个故事都必须单独满足上述条件。技术层次、角色人数和执行阶段不是拆分依据。技术工作也要说明实际使用者，例如维护者、运维人员或下游开发者，以及他们能使用的结果。

贡献必须由故事自己写明「对目标的贡献」；没有上层目标时写清本故事自身即有效目标，不把标题或同项目其他目标的内容当作贡献。上层目标的验收条件以上层目标记录为准，故事模板只写本故事的标准，两者分别标明归属和来源。开工、每次实质交接和终验前重新读取任务上下文；正文没有可提取的验收条件时如实标注信息不足，不用标题补全，也不虚构归属。最终结果或成功标准发生实质变化时重审整份计划及所有关联故事；路线改变时只重评受影响的依赖和相关故事。

## 结项记录

将以下记录放在原任务中，用户不必翻阅运行日志就能知道做成了什么。

```markdown
已交付：[用户故事与实际结果]
产物：[可打开的链接、共享正文或附件]
查看或体验：[最短操作步骤、必要环境与权限]
体验数据：[使用哪些示例数据；是否独立于日常数据]
反馈与复验：[原事项入口、接收负责人、最新体验版本]
验收：[逐条通过、失败或未验证及证据入口、执行版本；必验项缺证据或失败时说明未整体通过，并写明责任人、回流路径与用户体验决定]
版本与限制：[实际版本、验证平台；合并、部署或其他未完成范围]
合并与清理（代码交付）：[PR 或合并提交、已清理分支与工作副本、仍需保留的体验入口]
```

先打开或读取报告，或按用户路径运行功能，再写验收结论。多机使用时，确认交付入口对用户可用；只有执行机上的文件路径不能证明已经交付。代码提交、日志和截图可作为证据，不能代替故事承诺的可体验功能。需要用户验收时写明待确认项；已有授权和验收证据足够时，不增加确认环节。

未满足关键条件时，写明缺口和接续负责人，保持实际状态。报告故事的产物可以是一份报告；功能故事不能用一份实现报告代替功能。不得通过改写验收条件把未完成工作包装成完成。

## 单工作区交付循环

1. 在日常工作区的原事项记录用户故事、反馈与验收。交付负责人使用项目资源指定的工作目录，按项目规则测试。
2. 交付前实际打开入口并按用户步骤操作。记录版本、验证平台、测试数据和限制。跨设备时核对入口可达性。
3. 有必需的用户验收时，原事项写明待体验内容。核对实际接收者，通过已有负责人或小队接续。用户反馈后在同一事项更新版本、入口和结果。
4. 验收通过后，集成负责人按仓库规则将已验收版本合入目标分支。确认合并结果后清理该故事已合并的临时分支和干净、闲置的工作副本。保留项目工作目录和未提交改动。
5. 按授权发布。涉及共享服务和数据时，先备份，在空闲时执行升级，并在同一日常客户端用真实项目复验。原事项记录合入、发布和复验的实际结果。
6. XShadow 平台版本由 Codex 在工作台接续。沿用个人第二大脑的项目目标、任务和分工。

## 示例：获得一份决策报告

- 标题：获得三种部署方案的对比报告，选定共享服务的部署方式。
- 用户故事：作为工作台所有者，我希望比较三种部署方案的成本、维护要求和多机访问方式，以便选择适合自己的方案。
- 交付物：一份包含比较表、建议、依据和未确定事项的报告。
- 交付入口：原任务中可直接打开的报告正文或附件，结项时提供实际入口。
- 验收：覆盖三种方案和上述比较维度；关键事实标明来源及日期；建议解释取舍；用户可打开完整报告。
- 执行清单：搜集资料、比较方案、核对事实、交付报告，均在这个故事内推进。

## 示例：体验按项目筛选任务

- 标题：在任务列表按项目筛选，快速找到当前项目的任务。
- 用户故事：作为同时管理多个项目的用户，我希望选择一个项目后只看到它的任务，以便集中处理当前项目。
- 交付物：约定客户端中可体验的项目筛选功能。
- 交付入口：约定测试环境的任务列表地址，或可取得的安装包及启动方式。
- 验收：选择项目后仅展示该项目任务；清除筛选后恢复列表；没有匹配任务时显示空状态；按约定平台实际验证并保留证据。
- 执行清单：交互设计、查询实现、界面接入、测试和独立验收，均服务这个故事。

以上入口是规划说明，不是已交付的地址。实际任务结项必须替换为可用入口。
