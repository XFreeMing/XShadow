# 按用户故事交付任务

创建或重新规划任务时，将下面的内容写进任务正文。小任务可合并成几句话，但仍需明确用户价值、产物、入口和验收条件。不要为了填写模板另建文档或审批任务。

## 任务正文

```markdown
标题：用户完成后能得到的结果

用户故事：作为[使用者]，我希望在[场景]下[得到结果或完成操作]，以便[解决问题]。
交付物：[具体报告、功能、工具或其他可使用的成果]
交付入口：[计划放在哪里，如何打开或体验；结项时替换为实际可用的链接或附件]
范围：[本次包含什么，哪些内容留待后续]
交付负责人：[一名对完整结果负责的人或角色]

验收条件：
- [给定条件，用户执行操作后，可观察的结果]
- [产物的内容、可访问性或必要的失败场景]

执行清单：[按需记录分析、设计、实现、验证与交接]
依赖或阻塞：[确实存在时，写明缺少什么、由谁提供、何时或由什么事件接续]
```

拆分故事时，每个故事都必须单独满足上述条件。技术层次、角色人数和执行阶段不是拆分依据。技术工作也要说明实际使用者，例如维护者、运维人员或下游开发者，以及他们能使用的结果。

## 结项记录

将以下记录放在原任务中，用户不必翻阅运行日志就能知道做成了什么。

```markdown
已交付：[用户故事与实际结果]
产物：[可打开的链接、共享正文或附件]
查看或体验：[最短操作步骤、必要环境与权限]
验收：[逐项结果及证据入口]
版本与限制：[实际版本、验证平台；合并、部署或其他未完成范围]
```

先打开或读取报告，或按用户路径运行功能，再写验收结论。多机使用时，确认交付入口对用户可用；只有执行机上的文件路径不能证明已经交付。代码提交、日志和截图可作为证据，不能代替故事承诺的可体验功能。需要用户验收时写明待确认项；已有授权和验收证据足够时，不增加确认环节。

未满足关键条件时，写明缺口和接续负责人，保持实际状态。报告故事的产物可以是一份报告；功能故事不能用一份实现报告代替功能。不得通过改写验收条件把未完成工作包装成完成。

## 示例：获得一份决策报告

- 标题：获得三种部署方案的对比报告，选定共享服务的部署方式。
- 用户故事：作为工作台所有者，我希望比较三种部署方案的成本、维护要求和多机访问方式，以便选择适合自己的方案。
- 交付物：一份包含比较表、建议、依据和未确定事项的报告。
- 交付入口：原任务中可直接打开的报告正文或附件，结项时提供实际入口。
- 验收：覆盖三种方案和上述比较维度；关键事实标明来源及日期；建议解释取舍；用户可打开完整报告。
- 执行清单：搜集资料、比较方案、核对事实、交付报告，均在这个故事内推进。

## 示例：体验按项目筛选任务

- 标题：在任务列表按项目筛选，快速找到当前项目的任务。
- 用户故事：作为同时管理多个项目的用户，我希望选择一个项目后只看到它的任务，以便集中处理当前项目。
- 交付物：约定客户端中可体验的项目筛选功能。
- 交付入口：约定测试环境的任务列表地址，或可取得的安装包及启动方式。
- 验收：选择项目后仅展示该项目任务；清除筛选后恢复列表；没有匹配任务时显示空状态；按约定平台实际验证并保留证据。
- 执行清单：交互设计、查询实现、界面接入、测试和独立验收，均服务这个故事。

以上入口是规划说明，不是已交付的地址。实际任务结项必须替换为可用入口。
