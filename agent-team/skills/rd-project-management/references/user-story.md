# 按用户故事交付任务

创建或重新规划任务时，将下面的内容写进任务正文。小任务可合并成几句话，但仍需明确用户价值、产物、入口和验收条件。不要为了填写模板另建文档或审批任务。

## 任务正文

```markdown
标题：用户完成后能得到的结果

用户故事：作为[使用者]，我希望在[场景]下[得到结果或完成操作]，以便[解决问题]。
交付物：[具体报告、功能、工具或其他可使用的成果]
交付入口：[计划放在哪里，如何打开或体验；结项时替换为实际可用的链接或附件]
范围：[本次包含什么，哪些内容留待后续]
交付负责人：[一名对完整结果负责的人或角色]
代码交付时的集成目标：[仓库、目标分支、集成负责人]

验收条件：
- [给定条件，用户执行操作后，可观察的结果]
- [产物的内容、可访问性或必要的失败场景]

开工评判：[可开工或退回结论、评判人、所评判的故事版本；退回时写具体反例、用户影响、责任人和最小修正]
验收测试映射：[逐条：验收条件 → 用例或手验项、命令或用户路径、预期结果、版本、证据位置；手验项说明不能自动化的原因和负责人]

执行清单：[按需记录分析、设计、实现、验证与交接]
依赖或阻塞：[确实存在时，写明缺少什么、由谁提供、何时或由什么事件接续]
```

## 开工评判与验收映射

新建或正式重规划的故事先由用户故事评判员给出可开工或退回结论，再进入实现。退回必须给出具体反例和责任人，由原负责人修正；评判员不自行改写故事。可开工后，实现与固定输入的测试准备并行推进，不等待最终验收。

验收自动化工程师把已认可的验收条件逐条映射为可运行的用例、命令、预期结果、执行版本和证据位置；优先复用已有测试并说明依据。无法自动化的手验项说明原因、步骤和负责人。跨入口影响、旧测试复用、范围或版本变化时按影响重验，未重验项写明理由。

质量交付经理对同一候选版本逐条记录通过、失败或未验证；必验项缺证据或失败时不得整体通过，并注明责任人、回流路径和用户体验决定。

简单或报告类故事轻量处理：写明使用者、产物、入口和可核对条件即可，不为填表另建文档、审批层、每阶段事项或重复唤醒。

拆分故事时，每个故事都必须单独满足上述条件。技术层次、角色人数和执行阶段不是拆分依据。技术工作也要说明实际使用者，例如维护者、运维人员或下游开发者，以及他们能使用的结果。

## 结项记录

将以下记录放在原任务中，用户不必翻阅运行日志就能知道做成了什么。

```markdown
已交付：[用户故事与实际结果]
产物：[可打开的链接、共享正文或附件]
查看或体验：[最短操作步骤、必要环境与权限]
体验数据：[使用哪些示例数据；是否独立于日常数据]
反馈与复验：[原事项入口、接收负责人、最新体验版本]
验收：[逐条通过、失败或未验证及证据入口、执行版本；必验项缺证据或失败时说明未整体通过，并写明责任人、回流路径与用户体验决定]
版本与限制：[实际版本、验证平台；合并、部署或其他未完成范围]
合并与清理（代码交付）：[PR 或合并提交、已清理分支与工作副本、仍需保留的体验入口]
```

先打开或读取报告，或按用户路径运行功能，再写验收结论。多机使用时，确认交付入口对用户可用；只有执行机上的文件路径不能证明已经交付。代码提交、日志和截图可作为证据，不能代替故事承诺的可体验功能。需要用户验收时写明待确认项；已有授权和验收证据足够时，不增加确认环节。

未满足关键条件时，写明缺口和接续负责人，保持实际状态。报告故事的产物可以是一份报告；功能故事不能用一份实现报告代替功能。不得通过改写验收条件把未完成工作包装成完成。

## 边使用边研发的交付循环

1. 日常客户端保存真实项目、用户故事与反馈。研发客户端使用独立工作副本、端口和数据库，在同一环境内完成开发、测试和用户体验。研发工作区按需准备示例数据，只有验证智能体执行时才初始化研发军团。
2. 一个故事指定一名集成负责人。各执行者可以使用独立工作副本，负责人把经过检查的结果集成到用户使用的研发客户端，并在原事项写明版本和功能入口。
3. 交付前实际打开入口，按用户步骤操作，记录实际版本、验证平台、测试数据和限制。跨设备时核对入口是否可达，不能把执行机的 localhost 当作所有设备可用的地址。
4. 需要用户体验决定时保持 in_review，原事项明确待体验内容。核对评论的实际接收者，优先复用已有负责人或小队接续，不叠加重复唤醒或定时轮询；没有接续证据时如实注明。
5. 用户在原事项反馈后，负责人按反馈协调修改、验证和重新交付，更新同一记录中的版本和入口。修正当前故事不另建重复任务；独立新增价值才作为另一个故事。不得模拟用户反馈或把没有反馈当作通过。
6. 验收通过后，项目经理通过原事项交给集成负责人合并。核对目标分支和已验收提交，按仓库规则执行。GitHub PR 有必需检查待完成时，启用该 PR 的自动合并或加入合并队列。条件已满足时直接合并。验收后提交有实质变化时，核验变化后再入队。合并与日常环境发布分别记录，发布按已授权范围安排持久化数据的备份、升级和回退。
7. 读回 PR 合并结果或确认提交已进入目标分支，再清理该故事的临时分支。远端使用仓库的合并后删除功能，并核对分支已移除。本地先核对工作副本干净、没有运行中的任务或服务、产物和验收证据已保存在可持续访问的位置，再移除工作副本并删除已合并分支。使用 squash 或 rebase 的仓库须核对已合并 PR 对应的源提交，避免删除后来新增的提交。保留长期研发环境、含未提交改动的工作副本及仍被其他任务使用的分支。分支清理不包含删除数据库。
8. 用户更新日常客户端后，用真实场景复验。原事项记录所用版本和结果。发现问题时回到研发客户端修正，再交付下一轮。可复用结论附来源事项、适用版本、复验方法和边界，按既有分工审核后写入模板或领域技能，并读回实际配置。机器路径、实例 ID 和临时排障留在项目记录。

## 示例：获得一份决策报告

- 标题：获得三种部署方案的对比报告，选定共享服务的部署方式。
- 用户故事：作为工作台所有者，我希望比较三种部署方案的成本、维护要求和多机访问方式，以便选择适合自己的方案。
- 交付物：一份包含比较表、建议、依据和未确定事项的报告。
- 交付入口：原任务中可直接打开的报告正文或附件，结项时提供实际入口。
- 验收：覆盖三种方案和上述比较维度；关键事实标明来源及日期；建议解释取舍；用户可打开完整报告。
- 执行清单：搜集资料、比较方案、核对事实、交付报告，均在这个故事内推进。

## 示例：体验按项目筛选任务

- 标题：在任务列表按项目筛选，快速找到当前项目的任务。
- 用户故事：作为同时管理多个项目的用户，我希望选择一个项目后只看到它的任务，以便集中处理当前项目。
- 交付物：约定客户端中可体验的项目筛选功能。
- 交付入口：约定测试环境的任务列表地址，或可取得的安装包及启动方式。
- 验收：选择项目后仅展示该项目任务；清除筛选后恢复列表；没有匹配任务时显示空状态；按约定平台实际验证并保留证据。
- 执行清单：交互设计、查询实现、界面接入、测试和独立验收，均服务这个故事。

以上入口是规划说明，不是已交付的地址。实际任务结项必须替换为可用入口。
