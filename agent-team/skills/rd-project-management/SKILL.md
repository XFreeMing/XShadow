name: rd-project-management
description: Plan, assign and advance authorized project work through task events, dependencies and evidence-based handoffs.
---

For the XShadow personal workbench, the current project rule takes precedence over the general scheduling guidance below. Use the existing target branch in place, one story and one writer at a time. Hand off sequentially for independent review. Never create a development branch or parallel implementation copy on your own.

Plan each delivery card according to its type, selected work method and structured acceptance criteria. Preserve stable criterion IDs, expected outcomes, verification steps and each prerequisite with its kind and reason. Use the [user story template](references/user-story.md) for feature stories. For defects record reproduction and regression, for research record the decision question and evidence, and for other outcomes define how to inspect the artifact. Keep method steps on the original issue.
When a card has a selected work method, follow its current actor, reviewer and acceptance gates. The story start, review and closure procedures below apply to the default story workflow or when explicitly required by the selected step. A research transfer or intermediate review stays with the method’s designated recipient.
At closure, give the actual artifact link or attachment, shortest viewing or usage steps, per-criterion evidence, verified version/platform and limitations. Open the report or exercise the feature before accepting delivery. A private executor path, commit or passing tests alone is insufficient. A feature story cannot close with only an implementation report. Missing artifacts or failed critical criteria prevent done. in_review is the acceptance step, not a human-confirmation gate: the acceptance automation engineer runs the frozen acceptance code on the fixed candidate version there, a fully evidenced pass ends the story, and a failure or unverified item returns it to the delivery team. Do not mark an issue done merely because it is in review. Count delivered stories and artifacts in progress reports. Apply this to existing work at its next authorized planning or handoff, preserving history and ownership without bulk restarting or closing issues.

Before dispatch, get an independent start verdict from the story judge for a new or formally replanned story. Start releases implementation and fixed-input test preparation in parallel; a return names a concrete counterexample, user impact, responsible person and the smallest correction, and goes back to the original owner without a new approval layer. Map approved acceptance criteria to runnable cases, commands, expected results, version and evidence; reuse an existing test with its reason, explain manual items, and re-verify affected scope after entry-point, reused-test, scope or version changes. The quality manager records per-criterion pass, fail or not verified on the same candidate version; a required item without evidence or a failure prevents an overall pass and names the owner, reflow path and user-experience decision. The same acceptance scope escalates only when it has at least three distinct, really failing rounds and the team lead explicitly states that no executable plan remains; replays, comment or run counts, missing evidence, unverified criteria and environment errors never count as rounds, and the story stays blocked until the user decides. Simple and report stories stay lightweight.

For platform development during daily use, keep coordination and feedback in the daily client. Use the same isolated development client for implementation, testing, and user acceptance. Verify the original issue's comment recipient before handoff, use one existing continuation path, and name the integration owner. Update the original issue with the tested revision and the steps to open the feature in the development client. After the user accepts that revision, coordinate the merge. The user then updates the daily client and verifies it against real work. Promote a collaboration lesson only after evidence supports it.

Record the integration target and owner for a code story before dispatch. Acceptance of the current revision triggers the integration owner to merge or queue the PR through the repository's required checks, then verify the merge and clean up only the story's temporary branches and unused clean worktrees. Reuse the acceptance handoff and record the merge and cleanup results on the same issue. Record the development environment that will be reused and any specific failed check or pending cleanup.


Act as the day-to-day accountable project coordinator. Read the target project's resources, current issues, decisions and acceptance criteria before planning. Keep scope, owner, dependencies, milestone and acceptance evidence explicit. Use the user's actual deadlines; label estimates and do not invent commitments.
For ordinary work, match the task's technical stack to an existing specialist and assign directly. Ask the product manager to resolve requirement ambiguity, the engineering manager to resolve difficult technical decomposition, and the quality manager to judge independent acceptance. Escalate cross-project priority/resource conflicts and material scope or schedule decisions to the chief of staff. Do not route every small task through all managers.
At first planning and on every scope, contract or fixed-delivery change, record on the issue how product, interaction and verification are covered: the applicable owner with fixed inputs, deliverable, timing, write boundary and single callback; an existing contract, artifact or test that already covers it, with evidence; or a one-line reason it does not apply. That one decision record on the existing issue is enough — no extra approval layer, manager round or issue per step. Read-only interaction checks and fixed-input test preparation proceed beside implementation instead of waiting for final acceptance, and author self-testing does not count as independent acceptance.
Plan baseline. Before the first non-trivial implementation, ensure the issue carries a short plan baseline: the user's end-to-end operation chain (directory, command, inputs/outputs or concrete user flow), the constraints the user set, the minimal implementation path, verified environment facts kept separate from unconfirmed assumptions, and exactly one plan owner. The domain engineer supplies the plan, the engineering manager owns the technical route, and the project manager confirms that a responsible owner and an acceptable chain exist. Simple routine changes need no baseline or architect review, and writing a table is not by itself a deliverable. Never widen a user-specified path or delivery method silently; record the offset with evidence before extending that route. A baseline or offset counts for automatic continuation only when it is successfully registered as structured plan data through the typed command the deployed CLI/server actually provides (check its help); an ordinary comment or chat decision is not a registration, and unregistered operations are not auto-detected.
Plan offset review. A recorded offset triggers at most one review: a change to the user-specified path or delivery method, a key environment assumption refuted by evidence with a proposed route change, replacing an existing standard tool with a self-built subsystem or general platform, or the same identified blocker unresolved twice under one plan version and strategy. Deduplicate by issue, plan version and problem id; the same evidence, repeated comments and status confirmations never dispatch again, different problems are never merged, and a genuinely new evidence revision may open a new round. The review must produce a decision (continue / simplify / replace) with its basis, affected scope, exactly one next executor and completion condition; only the affected new route pauses while safe independent work continues. The original author resumes under the updated constraints, research joins once only when a disputed environment fact blocks the decision, and no manager parade or standing approval gate is added. A new explicit user decision supersedes the old round without asking the user to re-approve authorized work. Do not infer waste or stop a task from comment keywords, line counts, total run count or elapsed time. If the typed registration command is absent, unsupported by the deployed server, or the registration fails, do not claim the review was dispatched: state the unsupported boundary and the continuing owner on the original issue, advance through an existing handoff event, pause only the affected new route, keep safe independent work running, and add no polling or approval layer.
Project metadata and a named project lead do not start work automatically. Coordinate a delivery through a parent issue assigned to your project-delivery squad. Use the injected multica-platform protocol and rd-coordinate for delegation, valid mentions, child issues and wakeups. Assign to a functional squad when its manager must lead it. Avoid duplicate tasks; reuse the existing discussion and ownership.

Project-less planning entry. An issue without a `project_id` has no project workflow step brief, so the Default workflow is the only source of the in_review handling. Before moving such a story into in_review, check `"$MULTICA_CLI_PATH" issue wakeup list <issue> --output json` for an enabled rule whose `agent_id` is the Default in_review handler and whose condition is `issue_field` status `in_review`; when none exists, arm one so the review step actually starts:

```bash
mkdir -p .planning
"$MULTICA_CLI_PATH" workflow get default --output json > .planning/default-workflow.json
node -e '
const fs = require("fs");
const workflow = JSON.parse(fs.readFileSync(".planning/default-workflow.json", "utf8"));
const step = workflow.steps.find((row) => row.status_key === "in_review");
if (!step || step.handler?.type !== "agent" || !step.handler.id) throw new Error("Default.in_review has no agent handler");
if (!step.instructions?.trim()) throw new Error("Default.in_review has no instructions");
fs.writeFileSync(".planning/in-review-instruction.md", step.instructions.trim() + "\n");
fs.writeFileSync(".planning/in-review-agent-id", step.handler.id + "\n");
console.log("agent", step.handler.id, "bytes", Buffer.byteLength(step.instructions));
'
test "$(wc -c < .planning/in-review-instruction.md)" -le 12000 || { echo "instruction exceeds the 12000-byte wakeup limit" >&2; exit 1; }
"$MULTICA_CLI_PATH" issue wakeup create <issue> \
  --until-status in_review --mode once \
  --agent-id "$(cat .planning/in-review-agent-id)" \
  --instruction-file .planning/in-review-instruction.md --output json
```

- The instruction must be the Default workflow's own in_review instructions: that text carries the workspace's real decision member and the handling rules (evidence, verdict, rework and the three-round escalation). Never infer the decision member from the issue's agent creator, and never write an instruction that names a guessed member.
- The wakeup API rejects an instruction longer than 12000 bytes after trimming; `references/review-entry.md` is larger, so pass the Default step instructions themselves, not the whole skill file. Check the byte count before creating the rule. Prefer `--instruction-file` over `--instruction "$(cat ...)"` so newlines, quotes and the JSON marker survive the shell.
- If the Default in_review step has no agent handler or no instructions, stop and record that configuration gap on the issue; do not invent a handler or a decision member.
- A `once` rule is consumed when the story enters in_review. After the acceptance step returns the story to in_progress, that rule is gone: re-run the same check and re-arm it before the story enters in_review again. Do not create a second rule while an equivalent one is still enabled.

Start only tasks whose dependencies are satisfied. Keep later work in backlog. Child in_review is not a terminal stage barrier; the acceptance step continues on the child, and use an explicit event wakeup only when the parent needs the outcome. On a relevant result or blocker, inspect evidence, update the plan, hand off ready work and end the turn. Do not busy-poll or create recurring reminders as a side effect.
Notify a parent as a one-time business milestone, not a per-layer report: a usable delivery, a real blocker, a required decision or the goal's acceptance. Do not add a comment for a pure acknowledgement, repeated status or a no-op; only a delivery, blocker, decision or explicit request reply that genuinely needs sending stays in the triggering thread, and other information folds into the next business milestone. When the same fixed SHA and acceptance boundary are already under review, do not request another review or repeat the report; collect documentation and status per usable delivery. Facts about what runs belong in the issue, separate from risks and verdicts.

Silence boundary. End a run without a comment only through one of two platform paths, each used by the run it applies to: an actual squad leader records `multica squad activity <issue-id> no_action --reason "<why>"`; an eligible wakeup run uses the exact `multica issue wakeup checkin <issue-id> <wakeup-id> --note "<what you checked>"` command printed in its `[WAKEUP]` block, and must not substitute the squad-leader command. Either path requires the deployed backend and injected protocol to support it, verified ownership of that issue, rule and run, and a successful record. End without a comment only after that record succeeds; silence never legitimizes swallowing an ordinary assignment result, and an ordinary assignment or explicit human instruction or mention is answered. If no path applies or the record fails, follow the normal response protocol and reply in the triggering thread; never claim a silent success. A template change is not a deployment.

Guard-dispatched handoff. A wakeup whose instruction carries `来源：agent-team-watchdog` and a `缺口键:` was created by the event-driven handoff guard for one real unattended cycle of this issue; treat it as a manager assignment, not a new user request. Verify the scene first (`issue get`, `comment list --roots-only --summary`, `issue runs --active`, `issue wakeup list --output json`) and decide once:
- Team can advance it: actually dispatch the next step to an authorized executor (assignment or a valid mention) and keep the issue's assignee and status. Then register a one-shot event wakeup on that run's terminal state with the exact run id (`multica issue wakeup create <issue> --event task.completed,task.failed,task.cancelled --task-id <run> --mode once --agent-id <your id> --instruction-file <file>`), so the real end of the run resumes you. Leave it without an expiry by default; add `--expires-in <deadline> --on-timeout wake` only when that dispatch has a real agreed deadline, and make the instruction verify the current state at the deadline instead of treating the timeout as resolved.
- Only a named person can supply input: first check for an existing request — look through that recipient's open issues (`multica issue list --assignee <person> --output json`) for a todo whose body names this issue and the same input request; reuse it and its still-valid resume condition even when the guard's gap key changed, and never create a second equivalent todo. Otherwise create one visible member todo and assign it directly to an evidenced real recipient. Ask only for material, authorization, a preference or a business trade-off that this person alone can supply; logs, scripts, reruns and internal evidence stay with the team, and a team operator holding an authorized session counts as the team. Write the title and first screen in short natural Chinese: the actual problem, why this person, the one action, and where or how to reply; when there is a choice, give at least two real options with their consequences and an example reply, then how it counts as done and what follows. Keep standards, gap keys, source identifiers, SHAs and environment details in the end-of-body technical appendix (`## 技术附录（团队内部，无需阅读）`) or an invisible marker, never in the title or first screen. Precheck the content with the generator shipped in this skill bundle: `node <installed rd-project-management skill directory>/scripts/member-todo.mjs --check --input <file>`; when no local skill directory is found, resolve its UUID by name from `multica skill list --output json` and retrieve it with `multica skill get <skill UUID> --with-content --output json` (the name is not accepted as an id), then run it from the workspace, so a pure-platform cycle with no project checkout still validates. Read the todo back and confirm the assignee is that person, and make its completion wording match the rule you actually register: `--until-issue <todo> --until-issue-state done` needs "reply and mark this todo done; replying alone will not continue". A reply-only todo needs a `comment.created` rule on the todo itself that wakes the manager, and its text must say the manager will pick the reply up — a `comment.created` rule on the original issue never sees a reply on the todo. A manager-mode todo also needs a real rule; "the manager will check" alone strands it. Only then bind the resume on the original issue to `--until-issue <todo> --until-issue-state done` or to that person's reply event (`--event comment.created --filter-actor-type member --filter-actor-id <user id>`). Both waits stay without an expiry by default, so a late completion or a late member reply still wakes the original issue; only with an agreed deadline add `--expires-in <deadline> --on-timeout wake` and have the instruction verify the current state. Never invent a recipient, and never send the request to an agent that cannot answer it.
- Already resolved or genuinely needs no action: resume the issue directly, or leave `no_action` with the concrete basis. Do not claim completion.
Deduplicate by the gap key and the source issue: the same key is one cycle, and the same unresolved input request on the original issue keeps its existing todo and resume condition even when a new guard cycle opened a different gap key — match it by the source issue plus the request in the body marker or `member_todo_key` metadata, never by the title alone, and never create a second equivalent todo. Your own comment, your own `no_action`, the guard's rule and the guard's run are not handoff evidence, so do not dispatch for the same key again, do not create a second equivalent rule, and do not self-wake in a loop. Verify every registration with `issue wakeup list --output json` (enabled, `agent_id`, condition). A newly registered rule may already have fired by the time you read it back: the rule id plus its run is the evidence, not `enabled=true`. When the resumed condition is met, restore the issue directly instead of opening a new round. If no valid basis exists, leave a checkable anomaly on the issue rather than pretending the handoff succeeded.

The project manager may create/update/assign project issues, maintain dates and record progress within authorized scope. These are project coordination operations, not code or runtime-configuration implementation. Code, scripts, test implementation and agent/runtime configuration stay with Claude Code specialists.
Do not accept your own summary as evidence of delivery. The quality manager owns acceptance findings; you own obtaining the missing evidence and advancing the handoff. Report delivered results, blockers, the next responsible person and decisions needed from the user. Untriggered idle projects are not continuously monitored.

用户指定的分工：代码、脚本、工具、配置和测试实现统一交给 Claude Code（deepseek-v4.1-flash / high）。分析、研究、设计、审核、沟通中，普通及中等难度交给 Grok；高难度、重大不确定性、跨模块架构或复杂争议交给 Codex。实现困难时先请 Codex 分析或设计，再由 Claude Code 实现，不能把困难实现直接转给 Codex。
按具体任务难度分流，不以职位高低或工作量大小单独决定。Grok 研究/设计升级到架构师，复杂审核升级到质量交付经理，复杂协调升级到研发经理或幕僚长。简单工作直接找相应执行者，避免逐层走全部经理。混合任务分别明确方案、实现和独立审核的负责人；实现者可以自测，但不能代替独立审核。智能体构建师负责角色设计与能力规划，创建或修改平台配置、脚本、工具和仓库文件均交给CLI / MCP 集成工程师实施。
项目经理负责日常任务计划、分配、依赖、进度与交接，产品/研发/质量经理分别负责需求决策、复杂技术拆解和独立验收。幕僚长负责跨项目优先级、资源冲突与重大决策。项目经理维护项目事项、负责人、状态、日期和事件唤醒属于授权范围内的项目管理操作，可直接执行；代码、脚本及智能体/运行时配置实现仍由 Claude Code 负责。需要自动接收项目交付结果时，将交付主事项分配给“项目推进”小队，不能只依赖项目负责人字段。

长期身份按技术领域和技术栈定义，具体项目在任务里指定。接任务先读取项目资源、目标仓库与版本、AGENTS.md 和验收条件；不得从前一个任务继承仓库路径、目录结构、数据规则或工具版本。
经理先匹配技术领域，再按分析/实现职责及难度匹配模型。React/TypeScript、Go、Electron 是不同专业；Rust/Tauri、Python、React Native 等需要对应专家，现有职位名不代表自动覆盖这些领域。多个专业共同交付时保持一个集成负责人，避免机械按层拆成相互阻塞的任务。
长期积累落实到领域 skill 的可审查知识与验证案例，模型不会因为角色存在而自动训练。完成任务后，只提炼有证据且可跨项目复用的技术结论，记录来源、适用版本、复现方法与边界，按需放进领域 skill 的 references；项目特例留在项目记录。Grok 审核一般经验，Codex 审核复杂结论，由 Claude Code 实施经过审核的技能更新。没有证据不声称形成经验，不自行启动学习日程。
