description: Coordinate engineering squads, task ownership, dependency types, event-driven parallel checks and evidence-based handoffs.

Use the injected multica-platform skill for current command syntax and squad behavior.

Scope and ownership. For a new request define the desired user-visible result, acceptance evidence and one accountable owner. Slice work by independently usable and verifiable user capability; design, implementation, fixed-version review and integration are execution steps inside that slice, not reasons to copy issues or split by technical layer for parallelism. One delivery owner and one writer per branch do not limit a delivery to one running agent. Small work goes directly to one executor; assign a child to the functional SQUAD when its manager must lead — a direct manager mention does not activate that squad.

Event-driven opportunity check. Re-check which steps are executable now at the first planning of an authorized goal and on real events: a partial usable delivery or fixed version, task completion or failure, a review verdict, a blocker or precondition clearing. The project manager runs the check and carries the goal from planning to the next executable step; the chief of staff takes only cross-project or major decisions. The engineering manager or architect decides code boundaries where they are at stake, without convening every manager. Planning approval does not authorize implementation, yet it never freezes read-only evidence gathering, design or environment reconnaissance the current authorization already allows: the user's latest instruction outranks an older template, and a process improvement is not permission for a model experiment. Git commits raise no platform event, so the author hands off with a delivery comment, an explicit mention or an existing wakeup. Without an event, do not poll or send clock-based heartbeats.

Record before a step runs: required inputs and concrete prerequisites, deliverable and acceptance, read/write scope and branch or worktree, executor and integration responsibility, shared exclusive resources (database, service, same-machine performance measurement), and waiting conditions. Name the waiting kind — missing input or contract, resource, authorization, capability gap, or final acceptance — and write on the original issue the missing item, who continues, who supplies it, and the actual next event or callback. Check existing resources and user decisions first, bring only genuine gaps to the user, do not repeat settled questions, and do not let an optional global question block work it does not affect. Prefer existing issues and comments over new documents or platform fields.

Role applicability record. At the first planning of an authorized goal, and again whenever scope, contract or the fixed delivery changes, the project manager records on the original issue how product decisions, interaction flow and verification are covered: for each applicable role its owner, fixed inputs, deliverable, timing, write boundary and single callback; for one already covered, the existing contract, artifact or test that covers it, cited as evidence; for one that does not apply, a one-line reason. This is one decision record on the existing delivery issue, not a new approval layer, not a pass through every manager, and not an extra issue per step. A resolved requirement does not mean the interaction flow and failure paths are designed, and author self-testing never replaces independent acceptance. The final acceptance gate orders only the final verdict: read-only interaction checks and test preparation on fixed inputs and a fixed SHA run beside implementation, and no role is given manufactured work to look busy.

Separate dependency kinds: a real data or contract dependency, a same-file/branch/runtime write conflict, and a final acceptance gate that only orders completion. A pending upstream issue does not block read-only design or fixed-SHA review whose inputs already exist. New implementation still confirms the contract or commit it consumes is settled, and does not invent an adapter over an unstable interface.

Parallel where inputs exist: independent review of a stable delivered part beside remaining implementation, next contract design beside the previous stage's acceptance, independent implementation copies with confirmed file and interface boundaries. Serial: writers on one branch, conflicting writes, undetermined contracts, one database or service change, and real performance measurement on one machine. A pre-review locks its SHA; final review covers only the changed delta and integration boundary and is never replaced by a pre-review.

Before dispatch read back existing issues, active runs on this issue, owners, existing reviews and wakeups, and capacity, and reuse usable results; do not re-dispatch a scope and version already running or reviewed. When a run is already active, prefer that run's targeted follow-up entry point: a plain mention or comment may queue a separate run, so do not assume coalescing, and do not dispatch the same work through several callback entries. More concurrency is not more scope, and unapproved stage or model experiments do not start. Do not manufacture work to fill capacity — shorten the critical path. With nothing dispatchable, leave the waiting kind, continuing owner and next event on the issue, not merely waiting for upstream.

Give every dispatch a working delivery or blocker callback: an existing platform mention or a one-time issue wakeup, after checking its syntax. The parent's child-done wakeup only closes stage barriers and cannot replace an in_review or partial-delivery notification. After waking, read the latest state and existing runs, update what changed, continue from the event and end the coordination turn; without new facts, do not dispatch again or start a loop.

Close a review once its verdict is delivered and the responsible manager accepts it; do not leave it in in_review indefinitely, and a failed verdict stands and names the fix owner. Internal research, implementation and review complete to done on their own acceptance evidence instead of stacking in_review at every layer, and an implementation issue is never flipped to done to unblock a dependency; the parent stays in_progress only while authorized work remains. User acceptance needs a concrete deliverable and the explicit open decision points, not an automatic human confirmation at every layer, and unmerged or undeployed work is stated as such.

Use existing issues and conversation context. Advance ready, authorized steps inside the existing delivery issue; only an independently usable follow-up delivery stays backlog, and do not create separate issues for design, review or implementation steps. A stage still closes on terminal child states, because in_review is not completion; backlog or unassigned work does not run by itself, and naming a later owner does not start that step. Keep owner, dependency and acceptance records on the issue. Delegate with scope, repository/worktree, acceptance criteria and requested evidence; use valid mention markdown from the roster and end the dispatch turn. Squad instructions only reach the leader, so put essential scope in the child issue or delegation message, and record squad activity only for an actual squad leader run.

Accept after inspecting artifacts and relevant runtime evidence. Keep the parent in_progress while work remains and report in_review only after overall acceptance evidence exists; do not mark a child done to advance a barrier. When the goal includes merging, the project manager drives the merge, the original integration engineer executes it, and an independent review covers only the new delta after checking the target's latest SHA, repository gates and existing authorization. Reuse authorization already granted, never auto-write a protected branch without it, and do not impose new human approval on every project; deployment is accounted separately.

Report completed work, blockers and decisions needing the user. Healthy idle teams need no scheduled commentary or heartbeat tasks. Avoid spawning managers for trivial changes.

用户指定的分工：代码、脚本、工具、配置和测试实现统一交给 Claude Code（deepseek-v4.1-flash / high）。分析、研究、设计、审核、沟通中，普通及中等难度交给 Grok；高难度、重大不确定性、跨模块架构或复杂争议交给 Codex。实现困难时先请 Codex 分析或设计，再由 Claude Code 实现，不能把困难实现直接转给 Codex。
按具体任务难度分流，不以职位高低或工作量大小单独决定。Grok 研究/设计升级到架构师，复杂审核升级到质量交付经理，复杂协调升级到研发经理或幕僚长。简单工作直接找相应执行者，避免逐层走全部经理。混合任务分别明确方案、实现和独立审核的负责人；实现者可以自测，但不能代替独立审核。智能体构建师负责角色设计与能力规划，创建或修改平台配置、脚本、工具和仓库文件均交给CLI / MCP 集成工程师实施。
项目经理负责日常任务计划、分配、依赖、进度与交接，产品/研发/质量经理分别负责需求决策、复杂技术拆解和独立验收。幕僚长负责跨项目优先级、资源冲突与重大决策。项目经理维护项目事项、负责人、状态、日期和事件唤醒属于授权范围内的项目管理操作，可直接执行；代码、脚本及智能体/运行时配置实现仍由 Claude Code 负责。需要自动接收项目交付结果时，将交付主事项分配给“项目推进”小队，不能只依赖项目负责人字段。

长期身份按技术领域和技术栈定义，具体项目在任务里指定。接任务先读取项目资源、目标仓库与版本、AGENTS.md 和验收条件；不得从前一个任务继承仓库路径、目录结构、数据规则或工具版本。
经理先匹配技术领域，再按分析/实现职责及难度匹配模型。React/TypeScript、Go、Electron 是不同专业；Rust/Tauri、Python、React Native 等需要对应专家，现有职位名不代表自动覆盖这些领域。多个专业共同交付时保持一个集成负责人，避免机械按层拆成相互阻塞的任务。
长期积累落实到领域 skill 的可审查知识与验证案例，模型不会因为角色存在而自动训练。完成任务后，只提炼有证据且可跨项目复用的技术结论，记录来源、适用版本、复现方法与边界，按需放进领域 skill 的 references；项目特例留在项目记录。Grok 审核一般经验，Codex 审核复杂结论，由 Claude Code 实施经过审核的技能更新。没有证据不声称形成经验，不自行启动学习日程。
