# 设计选择和测试证据

在原故事的标准下选一种能揭示错误的实验，保留输入、预期、实际、版本和入口。以下操作是对原书的工程化应用。书中的结论和团队在某个系统上测出的结果分别记录。

## 从业务变化推到代码

| 故事中的问题 | 如何做出决定 | 如何识别选错 |
| --- | --- | --- |
| 两个团队使用同一个词 | 从双方各取一个实例，写出词义、标识、负责人、上下游及翻译规则。把共同定义限制在相应上下文。 | 用上游合法、下游无此含义的输入跑转换，观察是否明确处理。 |
| 改了名称还是同一对象吗 | 实体沿生命周期保留身份；金额、区间等值对象明示单位、相等性与不可变约束。 | 验证同名不同身份、同值不同实例、修改一个值后原值保持原状。 |
| 哪些状态必须一起合法 | 从一次业务操作识别立即一致的不变量和聚合根，把规则放在能拒绝非法变化的入口。 | 同时提交两个基于同一旧版本的合法请求，核对最终状态与冲突反馈。 |
| 规则由谁执行 | 放进实体或值对象能表达的规则由对象维护；跨对象的纯领域运算可用领域服务；应用层负责调度事务与外部依赖。 | 再从不同应用入口调用同一业务操作，用非法输入核对是否仍能绕过规则。 |
| 何时需要仓储 | 让用例以业务身份取回并保存聚合；单独设计读视图的筛选、排序和延迟合同。 | 在真实存储上保存后重新加载，核对身份、关联和规则；更新后对读侧检查承诺的可见时点。 |
| 现有边界要不要拆 | 固定用户场景，记录变更频率、团队依赖、伸缩压力和部署代价；模块单体也能保持上下文边界。 | 用一次真实变化比较涉及的模块、团队和发布单元。需要弹性收益时加负载实测。 |
| 跨系统提交与通知 | 先确定业务请求标识、去重范围与有效期。按故事约定验证中断后可恢复投递；若选择发件箱，核对业务写入与待发事件在同一事务提交。对本地副作用，消费者原子地保存去重记录与处理结果；对外部副作用，核对对方的幂等或对账合同。 | 分别注入提交前失败、提交后投递前中断、消费完成后确认丢失。重试同一操作只产生一次业务效果；同一对象再发起独立合法操作，两次效果都应保留。 |
| 事件历史和长流程 | 对确需历史还原的规则，用有版本的事件重建指定时点；长流程标出不可回滚的外部操作和业务补偿。 | 对照快照与重放，测试重复或迟到的事件、补偿失败以及再次恢复。 |
| 迁移旧系统 | 选一个调用入口，固定旧行为，逐步迁移调用者；每一步保留回退点。架构依赖约束单独验。 | 在同一输入下观察旧入口和新入口，重跑故障分支；架构检查通过后仍要核对用户结果。 |

原书定位：Otávio Santana《Domain-Driven Design with Java》电子版第 1–5 章，分别涉及业务目标、子域与上下文映射、实体/值对象/聚合/仓储、行为与架构测试、单体/服务/遗留重构。Vladik Khononov《Learning Domain-Driven Design》PDF 第 83 页讨论上下文图，第 108 页讨论值对象，第 137 页讨论并发，第 171 页讨论发件箱。以上提供缺少原笔记时按主题工作的依据；E032–E069 是笔记编者的编号，不能从书中页码反推逐条原意。

## 从可见行为选择测试层次

| 遇到的信号 | 操作与判据 |
| --- | --- |
| 实现返回固定值也能绿 | 选一个迫使结果变化的第二例，再做最小泛化。能直接写清一般规则时直接实现。Beck《Test-Driven Development: By Example》节选 PDF 第 24 页。 |
| 边界上存在两条同时成立的规则 | 先确认业务优先级，再断言两条件同时成立的结果。覆盖率只用于发现未执行的路径，逐个确认关键断言能拒绝哪种错误。 |
| 几个测试一起因改名、重复准备数据而坏掉 | 追踪哪一项业务行为受影响；共用环境安排可提取，各测试保留自己的可见预期。迁移公共接口时逐个迁调用者。 |
| 多个测试都在核对内部调用次序 | 优先断言输出、持久化状态或对外承诺。次数、顺序本身涉及付款、通知或审计义务时才写入合同。 |
| 外部服务慢、不稳定或难以制造特定失败 | 根据实际障碍选择 stub 的固定响应、fake 的小型行为实现、spy 的事后记录或 mock 的交互期望；用同一份接口样例核对真实适配器。 |
| 单元测试全绿，部署后依赖连接失败 | 分开运行核心规则、真实适配器的窄集成、生产创建路径的装配验证。依赖由构造器传入时单独查工厂与配置；使用 Nullable 时检查整条副作用链。 |
| 测试逼着开发者暴露私有方法或抽象父类 | 先从外部场景约束需保护的行为；新职责有独立业务含义时再抽取。逐个子类验证具体合同，包括与父类不同的前置条件或结果。 |
| 不熟悉的旧模块缺少测试 | 在拟修改范围找到可控接缝，记录真实输入、所有重要输出和副作用。对既有异常区分“当前如此”和“用户要求如此”，再写新行为的红灯。 |
| 有很多绿测但仍容易漏错 | 挑可能潜入的错误实现，比较它和正确实现在哪条断言分开。对照测试名、实际约束、错误类型和失败信息。 |
| 声称采用 TDD 降低返工 | 留存基线、训练或改造成本、交付物、返工原因和观察窗口；区分后验复跑与开发时的先红。对照故事可比时再估计效果。 |

来源包括 Myers《Essential Test-Driven Development》第 2–7 章及第 8 章收益讨论，特别是 PDF 第 201、222、251 页的多个替身、Nullable 和表征测试；Garcia 与 Farcic《Test-Driven Java Development》第二版第 3 章的行为边界与覆盖率；Johnson《Mastering Test-Driven Development》对红绿重构的讨论。书中示例是否满足本故事的规则，由原标准与真实入口决定。[Notion 研习与补证](https://app.notion.com/p/41c0cfe0ebfa816bb2f3f49c82885fb7)
