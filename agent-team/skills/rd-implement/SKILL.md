---
name: rd-implement
description: Implement scoped changes in the task-specified repository with isolated ownership and project-specific checks.
---

Implement the current user story through to its promised usable artifact. Read the beneficiary, scenario, value, delivery entry point and acceptance criteria before changing code; resolve genuine missing requirements in the original issue. Keep technical steps within the story. Deliver the agreed runnable feature, package or tool with an accessible entry point, exact version, shortest usage steps, actual verification evidence and remaining limitations. A commit or passing tests alone is not delivery of an experienceable feature. Do not claim done when the promised artifact is unavailable or a critical criterion fails; name the gap and continuing owner.


Resolve the repository, revision/worktree, scope and acceptance criteria from the current task and linked project resources. Do not assume a default project or copy a previous project's path or architecture. If the target is ambiguous, resolve that before edits. Read the target AGENTS.md, applicable nested instructions, manifests and build/test commands.
Plan checkpoint. Before the first non-trivial implementation, confirm the issue records the plan baseline: user operation chain, constraints, minimal path, verified facts versus unconfirmed assumptions, and one plan owner. If it is missing, ask the plan owner rather than inventing one. Before changing a user-specified path or delivery method, changing route because evidence refutes a key environment assumption, replacing a standard tool with a self-built subsystem, or extending a route after the same identified blocker failed twice under one strategy, register the offset with evidence through the typed plan command the deployed CLI/server actually provides (check its help) and wait for the decision that names the next executor and completion condition. A simple routine change needs neither, and recording never substitutes for the actual work. The platform auto-continues only after a baseline or offset is successfully registered as structured plan data; an ordinary comment, status confirmation or chat decision is not a registration, and unregistered actions are not auto-detected. If that command is absent, unsupported by the deployed server, or the registration fails, do not claim a dispatch or wait silently: state the unsupported boundary, what stays paused and the continuing owner on the original issue, advance through an existing handoff event, pause only the affected new route, keep safe independent work running, and add no polling or approval layer.
Inspect git status and preserve existing user work. Use the assigned worktree or the target repository's supported isolation workflow. Do not assume an isolated checkout includes another checkout's uncommitted changes. One writer owns each branch/PR.
Apply the target project's architecture, API compatibility, data and release rules. These are project context, not universal properties of a language. Make the smallest complete change and verify observable behavior with relevant project checks. Report exact revision, files, commands/results and remaining unverified criteria. Follow the target's evidence requirements for UI changes.
Publishing, releases and external messages follow the user's actual authorization. Do not invent an approval requirement for ordinary local fixes.
